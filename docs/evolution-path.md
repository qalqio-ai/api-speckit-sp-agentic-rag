# Product stages and tooling adoption

## Product stages (not tool installation stages)

1. **Stage 1: reusable API.** Preserve the current read-only R1 and health contracts.
2. **Stage 2: appended Agentic RAG.** Extend this repository after governance and
   reviewed scenario/corpus/feature decisions; do not replace the API foundation.

The supplied starter's tool-adoption stage numbers are not the product roadmap.

## Governance and tooling boundary

The initial-scope and R1 specs coexist: the former records repository sequencing,
the latter remains the implemented feature contract. Existing historical plans
are preserved, including their earlier absence-of-constitution statements.

Inspection found `.specify/feature.json` and R1 feature documents but no
`.specify/memory/constitution.md`, templates, or command scaffold. Official Spec Kit
initialization/version is not established by these artifacts. Keep the constitution
solely in [docs/constitution.md](constitution.md) until official adoption is confirmed.

For separately authorized official adoption:

1. Confirm harness, version and official setup procedure; inspect generated changes.
2. Preserve existing specs and user work; do not copy starter `.specify` files or
   hand-write tool internals.
3. Merge all ten approved principles into the official active constitution, with
   review of any tool-provided rules and conflicts.
4. In that same change replace `docs/constitution.md` with a link-only pointer to
   the active constitution. Update navigation and verify exactly one authority.
5. Record adoption/version and actual validation; do not claim installation from
   feature artifacts or from a skill exposed to this session.

Consult maintained [Spec Kit](https://github.com/github/spec-kit) and
[Superpowers](https://github.com/obra/superpowers) guidance at the time of adoption.
Do not copy upstream skills. Repository rules govern domain scope and authority;
tools supply workflow support, not permission to publish or change policy.
